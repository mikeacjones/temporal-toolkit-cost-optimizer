title: Many Updates rejected by the Workflow
why_it_costs: A rejected Update is one Action, the same as an accepted one, and it never appears in Event History, so history-based estimates miss it.
fix: Check what you can on the client before sending the Update, and reuse the Update ID when retrying so Temporal de-duplicates it. Don't rely on the Update validator to filter traffic you expect to reject.
tradeoffs: Client-side checks can go stale. Keep the validator for correctness; the client check only stops Updates you know will fail.

At least one in ten Updates to this Workflow Type is rejected by its validator. Each rejection is billed as one Action and leaves nothing in history. A common cause is using Updates as a lock or concurrency slot, where most callers are turned away, or clients retrying an Update with a new Update ID each time.

Send the Update only when the client has reason to think it will be accepted, and give retries the same Update ID so Temporal de-duplicates them instead of billing each one. If many callers compete for one slot, have them wait in a queue Workflow, or use a design that tells callers where they stand without an Update each time.
