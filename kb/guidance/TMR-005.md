---
id: TMR-005
title: Workflow whose first command is a Timer
why_it_costs: The Timer is an Action, and the Workflow's history sits in Active Storage while it waits. A start delay defers the first Workflow Task without starting a Timer.
fix: Start the Workflow with a start delay and remove the leading sleep.
tradeoffs: With a start delay, no Workflow code runs during the wait, so Signals sent then are handled after it. That is usually what a delay means. Whether a start delay is billed differently from a Timer is still being confirmed, so treat the saving as an estimate.

In each matching run, the first Workflow Task's only command is a Timer, and it fires before anything else happens. That is a delayed start written as a sleep. Timers that a Signal or Update cancels or races are waits, not delays, and tcopt doesn't flag them.

Move the delay to the caller's start options. When the Workflow only runs one Activity after the Timer, WF-002 suggests a Standalone Activity instead.
