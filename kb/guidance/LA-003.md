---
id: LA-003
title: Local Activity outlives the Workflow Task timeout
why_it_costs: While a Local Activity runs longer than the Workflow Task timeout, the SDK heartbeats the Workflow Task by completing it with no commands and starting another. Each heartbeat is one Action, and Local Activities re-run after a heartbeat can be billed again.
fix: Run work that can take longer than a few seconds as a regular Activity, or tighten the timeouts on the calls inside the Local Activity so it finishes well within the Workflow Task timeout.
tradeoffs: A regular Activity adds a round trip through the server. Raising the Workflow Task timeout instead delays recovery when a Worker crashes mid-task.

History shows Workflow Tasks that completed with no commands and were followed at once by another Workflow Task, before a Local Activity marker. Those are Workflow Task heartbeats: the SDK's way of keeping a long Local Activity alive. Workflow Task timeouts before the marker point to the same problem when the SDK couldn't heartbeat in time.

The estimate counts one Action per heartbeat. The Workflow can't handle Signals or Updates until the Local Activity finishes, which is another reason to make it a regular Activity.
