id: ACT-001
title: Retry storm
why_it_costs: Every Activity retry is one Action. An Activity that retries dozens of times against a failing dependency multiplies its cost by the number of attempts.
fix: Cap MaximumAttempts, raise InitialInterval, and return a next retry delay that matches how long the dependency needs to recover.
tradeoffs: A cap means some Activities fail instead of eventually succeeding. Handle that failure in the Workflow, or pause the Activity and resume it after the outage.

The Activity ran more attempts than tcopt's threshold of 10. The default Retry Policy retries forever, starting at 1 second and backing off to 100 seconds, so a dependency that's down for half an hour produces dozens of billed retries per Activity, across every Workflow waiting on it.

Set a retry limit that fits the call. For calls that fail because the other side is overloaded or rate-limited, return an Application Error with a next retry delay so the Activity waits as long as the dependency asks. For long outages, pausing the Activity stops the retries until someone resumes it.

The estimate counts the retries past attempt 10, which a cap at 10 would remove.
